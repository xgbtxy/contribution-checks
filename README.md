# DataFusion #26691 baseline check

This diagnostic builds the official SQLLogicTest runner from Apache DataFusion commit `039c0b99d5b05e73ff5def029c0131b76b481c6f` and runs four five-row SQL files from isolated temporary `test_files/` directories. The DataFusion checkout stays unchanged.

`oracles/issue-on.slt` is the reproduction reported by `@jayzhan211` in [DataFusion issue #26691](https://github.com/apache/datafusion/issues/26691), not an independent discovery. Its hand-written answer is the correct result (`a -2`, `d -3`). `issue-off.slt` uses the same oracle with the original TopK aggregation switch disabled. `positive.slt` sorts by a renamed direct aggregate column and includes computed siblings. `distinct-probe.slt` explores a separate computed projection over distinct values.

The workflow runs manually on `ubuntu-24.04`, checks out the pinned source with recursive submodules, installs Rust 1.99.0 and `protoc`, then builds with the locked CI-profile SQLLogicTest command and `--no-run`. The receipt records that compilation executes zero test cases, captures Cargo's full JSONL stdout and stderr, verifies a successful `build-finished` event, and records the runner binary SHA-256. The runner then uses Cargo's reported executable and requires exactly one completed test file for each invocation.

For each scenario, an independent `--complete` copy observes actual rows and the physical plan; the hand-written oracle stays intact. The core diagnostic passes only if the issue-on completion copy produces the reported wrong rows and `AggregateExec lim=[2]`, the hand oracle fails with exactly one result mismatch, issue-off returns the correct rows without an aggregate limit, and the positive control returns its correct oracle rows with at least one aggregate limit. The positive plan's node order is recorded without a hierarchy assumption.

The distinct probe is exploratory. Its actual rows, oracle exit, and whether the oracle confirms an additional wrong-result mismatch are recorded. A confirmed mismatch is classified `additional_result_mismatch` and does not fail the core diagnostic. Execution errors, missing files or plans, zero-file runs, failed core expectations, or source changes still fail the workflow.

The seven-day artifact contains the receipt, complete stdout/stderr logs, Cargo JSONL, case results, physical plans, and the four SLT files generated by `--complete`. It omits Cargo `target/` and the DataFusion source tree.

Run `python run_baseline.py --self-check` to validate the hand-written oracles without compiling DataFusion. The GitHub Actions workflow is the native execution path.
